## 지금 상태

브랜치 `design/terminal-light` 가 `main` 보다 커밋 10개 앞서 있습니다. 작업
트리는 깨끗하고 빌드·타입·린트가 모두 통과합니다. **아직 push 하지 않았고 PR도
없습니다.**

맥 터미널 컨셉으로 전체 화면을 다시 그렸습니다.

- 라이트를 기본으로 두고 다크를 같은 토큰으로 받습니다(`light` / `dark` /
  `auto`). 전환 버튼은 진입 화면에만 있습니다.
- 강조색은 파랑 하나, 빨강은 문제, 초록·호박·회색은 3단계 배지 안에서만.
- 진입 화면은 창 하나이고, 나머지 화면은 제목 위에 `$ 명령` 한 줄이 붙습니다.
- 제안 카드는 줄글 대신 해볼 것 목록(`steps[]`)이고, 고른 항목을 마크다운
  체크리스트로 내보냅니다.
- 고른 경험이 제안 목록에 실제로 반영됩니다(`coversItemIds` / `fromItemIds`).

**디자인 규칙은 [`design-system.md`](./design-system.md) 에 있습니다. 화면을
건드리기 전에 먼저 읽으세요.** 색·타이포·모서리뿐 아니라 왜 그렇게 정했는지가
함께 적혀 있습니다.

## 다음 순서

### 1. PR 올리기

지금 바로. 이후 작업이 이 브랜치 위에 계속 쌓이면 리뷰가 어려워집니다.

### 2. 역매칭 3단계 — `reverseMatch()`

**가장 큰 구멍입니다.** `apps/web/src/lib/personalize.ts` 의 `reverseMatch()` 가
비어 있어서 `/match/{직무}/result` 의 fit·step·far 세 칸이 모두 빈 채로
나옵니다. 서비스의 두 갈래 중 "경험부터 시작하기" 쪽이 끝까지 가지 못합니다.

화면과 디자인은 이미 다 되어 있습니다. 규칙만 정하면 됩니다.

지킬 것(코드 주석에도 적혀 있습니다):

- 3단계를 모두 노출합니다. "지금은 거리가 있어요" 를 비우지 않습니다.
- 순위를 매기지 않습니다. 회사를 줄 세우는 화면이 아닙니다.
- 점수나 퍼센트를 만들지 않습니다.

이미 만들어 둔 패턴을 그대로 쓸 수 있습니다. 회사별 제안에 적힌
`fromItemIds` / `coversItemIds` 와 고른 경험이 얼마나 겹치는지를 봅니다 —
겹치면 `fit`, 한 항목만 모자라면 `step`, 그 밖은 `far`. 데이터에 적힌 사실만
쓰므로 추측이 들어가지 않습니다.

### 3. 회사 데이터 채우기

`data/fixtures` 의 20개 파일 중 **`oliveyoung/backend.json` 하나만 내용이 있고
19개는 빈 껍데기입니다.** 나머지 회사는 화면에서 "준비 중" 으로만 보입니다.

파이프라인은 아직 수집 단계라 당장 데이터를 뽑지 못합니다. 일정이 급하면
두세 개를 손으로 채우는 편이 현실적입니다. 형식은 `oliveyoung/backend.json` 을
그대로 따릅니다 — `steps[]`, `coversItemIds`, `fromItemIds` 까지 포함해야 화면이
제 기능을 합니다.

**단, 아래 "계약이 둘로 갈라져 있습니다" 를 먼저 읽으세요.** 지금 손으로 채운
파일은 파이프라인이 만들 형식과 다릅니다.

### 4. 파이프라인

수집과 분석. 3번을 손으로 채웠다면 그 파일이 곧 출력 형식의 본보기입니다.

### 셋으로 나눈다면

파일이 겹치지 않게 자른 것입니다. 순서로는 A 가 B·C 를 막고 있습니다.

- **A. 계약 정하기 + 데이터** — `packages/contracts` 와 `types/data.ts` 중 어느
  쪽에 맞출지 정하고, `data/fixtures` 를 채웁니다. 위 2·4번.
  건드리는 곳: `data/`, `packages/contracts/`, `types/data.ts`
- **B. 역매칭 규칙** — `reverseMatch()` 를 구현합니다. 위 1번. 세 단계를 모두
  열어 두고, 점수도 순위도 만들지 않습니다.
  건드리는 곳: `apps/web/src/lib/personalize.ts`, `ReverseResult.tsx`
- **C. 파이프라인** — 수집에서 출력까지. main 에서 이미 진행 중이라 그 사람이
  이어가는 편이 낫습니다.
  건드리는 곳: `pipeline/`

## 이어받기 전에 알아 둘 것

- **데이터에 백엔드가 없습니다.** 파이프라인이 JSON 을 만들고
  → `data/published/` 에 놓이면 → 빌드 시점에 읽어 정적으로 굽습니다. DB 도 API
  서버도 없습니다. `data/published/` 가 비어 있으면 `data/fixtures/` 를 읽습니다
  (`apps/web/src/lib/data.ts`).
- **계약이 둘로 갈라져 있습니다.** 2026-09-13 main(#52)에 `packages/contracts`
  JSON Schema 와 `pipeline/src/career_compass_pipeline/contracts.py`(문서 간 참조
  검증)가 들어왔습니다. 그런데 그 스키마는 화면이 읽는 형식과 다릅니다:

  | 화면 (`apps/web/src/types/data.ts`) | 계약 (`company-project.schema.json`)         |
  | ----------------------------------- | -------------------------------------------- |
  | `suggestions.new[]` / `.deepen[]`   | 제안 하나가 문서 하나                        |
  | `steps[]` (할 일 여러 줄)           | `body` (문단 하나, 600자)                    |
  | `coversItemIds` / `fromItemIds`     | `entryExperienceIds` / `bridgeExperienceIds` |
  | `domainId`                          | `trackIds`                                   |
  | 경험 항목 id — `rest-api`, `crud`   | `rest-api-design` 등 다른 어휘               |

  스키마는 `additionalProperties: false` 라 여분의 필드를 실어 보낼 수도
  없습니다. **둘 중 무엇이 진짜 계약인지 정하는 일이 데이터 채우기(3번)보다
  먼저입니다.** 지금 손으로 채운 fixture 는 파이프라인이 만들 형식이 아닙니다.

- **`data/fixtures/oliveyoung/backend.json` 이 유일한 완성 데이터 샘플입니다.**
- 폴더 구조는 바꾸지 않기로 했습니다. 새 파일은 기존 폴더 안에 둡니다.
- 저장하지 않는 것들 — 경험 입력과 테마는 브라우저에만, 고른 제안은 메모리에만
  둡니다. 로그인이 없어서 지켜 줄 수 없는 것을 지켜 주는 척하지 않기로 했습니다.
  자세한 이유는 design-system.md 의 "선택과 내보내기" 에 있습니다.
