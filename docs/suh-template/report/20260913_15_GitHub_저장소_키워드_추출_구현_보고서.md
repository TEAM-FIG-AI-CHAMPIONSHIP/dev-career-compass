# GitHub 저장소 링크 기반 키워드 추출 기능 추가

## 개요

`/match/[role]/repository` 화면에서 사용자가 GitHub 공개 저장소 링크를 최대 3개까지 입력하면, 서버가 각 저장소를 훑어(언어 비율 + 설정 파일) 표준 기술 키워드를 추출해 화면에 보여준다. 저장소 주소와 추출된 키워드는 어떤 서버에도 저장되지 않고 브라우저에만 남으며, URL(쿼리 파라미터 등)에도 노출되지 않는다.

## 변경 사항

### 화면 (apps/web/src/app/match/[role]/repository, apps/web/src/components/experience)
- `page.tsx`: 기존 공용 헤더 대신 이 화면 전용 헤더(← 처음으로 / 1.직무 → 2.GitHub → 3.경험 단계 표시)와 GitHub 아이콘 배지 + 안내 문단으로 교체
- `RepositoryForm.tsx`: 저장소 최대 3개 입력, 분석 진행 상태(로딩/완료/실패)를 필드별로 표시, 분석이 끝나면 결과를 화면에 유지한 채 한 번 더 눌러야 다음 단계로 넘어가도록 함
- `RepoField.tsx`: `사용자명/저장소` 축약 입력 대신 전체 URL(`https://github.com/username/repo`) 입력으로 변경
- `icons.tsx`: GitHub 아이콘, 뒤로가기 화살표 아이콘 추가

### 서버 (apps/web/src/app/api/repo-keywords, apps/web/src/lib)
- `route.ts` (신규): `POST /api/repo-keywords` — 저장소 링크를 받아 GitHub 공개 API로 저장소 존재 여부/언어 비율/전체 파일 트리를 조회하고, 인식 가능한 설정 파일(`package.json`, `requirements.txt`, `pyproject.toml` 등)을 찾아 키워드를 추출해 응답. 아무것도 저장하지 않음
- `repo-keywords.ts` (신규): URL 파싱(`parseGithubUrl`)과 규칙 기반 키워드 매칭 로직 — 클라이언트와 서버가 같은 파싱 규칙을 공유
- `match-flow-store.ts`: 세션 저장 항목에 `repositoryKeywords`(저장소 URL → 추출 키워드) 필드 추가

## 주요 구현 내용

### GitHub 저장소 주소(최대 3개)가 넘어가는 방식

1. **입력 단계** — 화면의 입력 필드 3개는 각각 하나의 URL 문자열을 담는다. 입력 중에는 컴포넌트 내부 메모리(React state)에만 있고 아직 어디에도 저장되지 않는다.
2. **분석 요청** — "분석하고 경험 선택으로"를 누르면, 형식이 올바른(빈 칸이 아니고 `https://github.com/사용자/저장소` 형태인) 값만 골라 저장소마다 하나씩 `POST /api/repo-keywords`로 보낸다. 요청 본문은 `{ "url": "https://github.com/..." }`이고, 최대 3개가 동시에(병렬로) 전송된다. 이 요청은 우리 서버를 한 번 거쳐 GitHub 공개 API를 조회할 뿐, 이 값을 데이터베이스나 파일에 저장하지 않는다.
3. **응답과 화면 반영** — 서버가 각 저장소에 대해 `{ ok: true, keywords: [...] }` 또는 실패 사유(`{ ok: false, reason: "not_found" | ... }`)를 돌려주면, 화면은 그 결과를 필드 아래 칩(또는 안내 문구)으로 보여준다.
4. **브라우저 저장** — 응답을 받는 즉시, 성공한 저장소 URL과 키워드 묶음을 **세션 스토리지**(`window.sessionStorage`, 키: `refactor.me.match-flow.v1`)에 저장한다. 저장되는 값은 `{ role, repositories: ["url1","url2",...], repositoryKeywords: { "url1": ["React", ...] } }` 형태다. 이 값은 이 브라우저 탭에서만 유지되고, 탭을 닫으면 사라진다. 페이지 주소(URL)에는 어떤 값도 실리지 않는다.
5. **다음 단계로 이동 시** — "경험 입력으로" 이동하는 순간, 세션 스토리지에 있던 저장소 URL 목록이 경험 입력 값(`ExperienceInput.repos`)에 실려 **로컬 스토리지**(`window.localStorage`, 키: `refactor.me.experience.v1`)로 옮겨지고, 세션 스토리지 항목은 그 자리에서 삭제된다. 추출된 키워드(`repositoryKeywords`)는 이 시점까지만 유지되며, 아직 이후 화면에서 소비하는 곳이 없어 이동과 함께 버려진다(카탈로그 자동 매핑은 이번 범위 밖 — 참고사항 참조).
6. **다시 이 화면으로 돌아오면** — 세션 스토리지에 남아 있는 동안은(같은 탭에서 뒤로가기 등으로 돌아왔을 때) 입력했던 저장소 URL과 방금 추출된 키워드가 그대로 다시 보인다.

요약하면 흐름은 `입력 필드(메모리) → POST 요청(일회성, 서버는 저장 안 함) → 세션 스토리지(탭 한정) → (다음 단계로 넘어갈 때) 로컬 스토리지`이며, 서버 쪽에는 그 어떤 단계에서도 영구 저장이 일어나지 않는다.

### 저장소 탐색 범위

처음에는 저장소 루트 디렉터리만 확인했으나, 하위 폴더에 설정 파일이 있는 모노레포(예: `backend/requirements.txt`, `frontend/package.json`)를 놓치는 문제가 있어 GitHub의 전체 파일 트리(`git/trees?recursive=1`)를 조회하도록 바꿨다. 한 저장소당 최대 5개 설정 파일까지만 가져와 API 호출을 억제한다.

## 주의사항

- `personalize.ts`(기업 분석과 비교하는 판단 로직)와 `data/experience.json`(기존 경험 체크 9개 항목)은 이번 작업 범위 밖이다. 추출된 키워드는 그 항목들과 매핑되지 않는 독립적인 일반 기술 키워드로만 존재한다.
- 키워드 인식 규칙(`KEYWORD_RULES`)은 22개 항목의 수작업 목록이라 다양성에 한계가 있다 — 확장 여부는 이슈 댓글에서 논의 중이다.
- 저장소 분석이 실패(비공개·존재하지 않음·GitHub API 지연)해도 다음 단계 진행은 막히지 않는다. "GitHub 없이 진행" 버튼으로도 언제든 건너뛸 수 있다.
- 서버가 GitHub API를 호출할 때 `GITHUB_TOKEN` 환경 변수는 선택 사항이다(있으면 요청 한도가 늘어남).
