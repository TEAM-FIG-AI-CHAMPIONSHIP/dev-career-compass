# GitHub 경험 후보와 회사 프로젝트 연결 설계

- 작성일: 2026-09-13
- 상태: 제품 방향 및 MVP 설계 합의 완료
- 범위: `직무 선택 → GitHub 분석 → 경험 확인 → 회사 연결`
- 선행 문서: `2026-09-12-repository-keyword-extraction-design.md`

## 1. 배경

현재 2단계 GitHub 분석은 저장소의 언어, 매니페스트와 Dockerfile에서 기술
키워드를 추출한다. 3단계는 이 기술 키워드를 경험 항목으로 보수적으로 매핑해
초기 선택값으로 사용한다.

이 방식에는 근본적인 간극이 있다. React, Redis, Kafka 같은 도구가 저장소에
존재한다는 사실은 사용자가 컴포넌트를 설계했거나 캐시와 메시징 시스템을 직접
구현했다는 사실을 증명하지 않는다. 특히 팀 저장소에서는 구현의 존재와 사용자의
담당 범위가 다를 수 있다.

또한 현재 `data/experience.json`은 화면과 개인화 흐름을 먼저 완성하기 위해 만든
임시 카탈로그다. 프로젝트 형태, 기술 문제, 직무와 참여 방식이 한 그룹에 섞여
있고, 회사 조사 결과의 프로젝트 제안과 연결되는 공통 ID도 아직 없다.

이 설계는 기술 키워드를 경험으로 바로 변환하지 않고, 저장소 근거로 경험
후보를 만든 뒤 사용자가 직접 확인하도록 흐름을 바꾼다. 확인된 경험은 회사가
다루는 프로젝트를 더 깊게 발전시킬 수 있는지 판단하는 출발점으로 사용한다.

## 2. 이해 요약

- 사용자는 네 상위 직무 중 하나를 선택한다.
- GitHub 입력은 선택이며 공개 저장소를 최대 3개까지 받는다.
- GitHub 사용자는 저장소 근거로 생성된 경험 후보를 검토한다.
- GitHub 미사용자와 분석 실패 사용자는 고정 경험 목록에서 직접 선택한다.
- 저장소에 구현이 존재해도 사용자의 담당 사실로 자동 확정하지 않는다.
- 사용자가 명시적으로 확인한 경험만 회사 매칭에 사용한다.
- 맞는 회사는 기술 스택이 많이 겹치는 회사가 아니라, 사용자의 기존 경험을
  회사의 근거 있는 프로젝트로 자연스럽게 발전시킬 수 있는 회사다.

## 3. 목표

1. 기술 존재와 수행 경험을 구분한다.
2. 모든 AI 후보에 저장소와 파일 근거를 연결한다.
3. GitHub 유무와 관계없이 동일한 경험 ID 계약으로 결과를 만든다.
4. 회사 조사 산출물과 경험 카탈로그가 같은 직무·세부 트랙·경험 ID를 사용한다.
5. 데모 규모에서 비용과 지연시간을 예측하고 제한할 수 있게 한다.
6. AI나 GitHub가 실패해도 회사 찾기 흐름을 완료할 수 있게 한다.

## 4. 명시적 비목표

- 비공개 GitHub 저장소 인증
- 커밋, PR, 이슈를 이용한 개인 기여도 분석
- 코드만으로 협업 방식이나 개인 역할 단정
- 코드에 없는 성능 수치나 결과 생성
- LLM을 이용한 회사 점수 또는 순위 생성
- 사용자 계정과 서버 측 경험 기록 저장
- 대규모 동시 처리, 작업 큐와 장기 실행 분석
- 최종 경험 카탈로그를 회사 조사 전에 확정

## 5. 핵심 원칙

### 5.1 저장소 근거와 사용자 사실을 분리한다

`구현 근거 있음`은 해당 구현이 저장소에 있다는 뜻이다. 사용자가 직접 구현했다는
뜻이 아니다. 모든 후보는 `내가 한 경험이에요`라는 사용자의 확인을 거쳐야 한다.

### 5.2 표시 문장과 매칭 ID를 분리한다

사용자에게는 저장소에 맞춘 구체적인 문장을 보여준다. 회사 매칭에는 팀이 관리하는
안정적인 경험 ID만 사용한다.

### 5.3 LLM의 판단 범위를 제한한다

일반 코드가 안전하게 수집하고 선별한 근거만 LLM에 전달한다. LLM은 저장소를
자율 탐색하거나 외부 URL을 방문하지 않는다. 정의된 경험 ID와 출력 스키마 밖의
결과는 폐기한다.

### 5.4 실패는 직접 입력으로 대체한다

GitHub 조회, 파일 선별 또는 LLM 분석이 실패해도 경험 입력을 막지 않는다.

## 6. 선택한 접근법

### 결정적 수집기 + 제한된 LLM 판정

1. 결정적 코드가 README, 파일 트리, 설정 파일과 직무 관련 핵심 소스를 선별한다.
2. LLM은 전달받은 근거 안에서만 경험 후보를 기존 경험 ID에 매핑한다.
3. 서버가 경험 ID, 파일 경로, 줄 범위와 근거 등급을 검증한다.
4. 여러 저장소의 동일 경험을 경험 ID 기준으로 합친다.
5. 사용자가 확인한 후보와 직접 선택한 경험만 최종 프로필에 저장한다.

다음 접근법은 제외했다.

- 기술 키워드에서 경험을 직접 매핑: 빠르고 저렴하지만 현재의 과도한 추론을
  해결하지 못한다.
- LLM 에이전트가 저장소를 반복 탐색: 유연하지만 호출 수, 비용, 지연시간과
  재현성이 데모 규모에 맞지 않는다.

## 7. 전체 데이터 흐름

```text
직무 선택
  ↓
공개 GitHub URL 입력 및 외부 API 전송 동의
  ↓
저장소별 근거 수집
  ├─ README
  ├─ 파일 트리
  ├─ 설정 파일
  └─ 직무 관련 핵심 소스
  ↓
Claude의 구조화된 경험 후보 판정
  ↓
서버 검증 및 여러 저장소의 중복 통합
  ↓
sessionStorage에 분석 결과와 검토 상태 보관
  ↓
사용자의 후보 확인 및 누락 경험 직접 추가
  ↓
확인된 경험 프로필을 localStorage에 보관
  ↓
회사 프로젝트의 진입 경험과 연결
```

기존 기술 키워드 추출은 유지하되 다음 용도로만 사용한다.

- 저장소 분석 요약 표시
- 직무 관련 파일의 우선순위 결정
- LLM에 전달할 저장소 기술 맥락

기술 키워드를 경험 ID로 자동 체크하는 현재 매핑은 새 흐름에서 사용하지 않는다.

## 8. 직무와 세부 트랙

MVP의 상위 직무는 현재 네 개를 유지한다.

- 서버·백엔드
- 웹 프론트엔드
- 데이터·AI
- 모바일

직무를 더 늘리는 대신 분석과 매칭에 내부 세부 트랙을 사용한다. 초기 예시는
다음과 같으며 최종 목록은 회사 조사 결과로 검증한다.

| 상위 직무 | 세부 트랙 예시 |
|---|---|
| 서버·백엔드 | 애플리케이션 서버, 플랫폼·인프라 |
| 웹 프론트엔드 | 서비스 UI, 디자인 시스템·성능 |
| 데이터·AI | 데이터 엔지니어링, 데이터 분석, ML·AI |
| 모바일 | iOS, Android, 크로스플랫폼 |

사용자는 1단계에서 상위 직무 하나만 고른다. 세부 트랙은 확인한 경험을 통해 복수로
연결될 수 있다. 화면의 회사 수는 하드코딩하지 않고 게시된 회사 조사 산출물에서
계산한다.

```json
{
  "version": 1,
  "roles": [
    {
      "id": "backend",
      "label": "서버·백엔드",
      "status": "published",
      "tracks": [
        {
          "id": "application-backend",
          "label": "애플리케이션 서버",
          "status": "published"
        },
        {
          "id": "platform-infra",
          "label": "플랫폼·인프라",
          "status": "draft"
        }
      ]
    }
  ]
}
```

새 세부 트랙은 `draft`로 추가하고 회사 근거와 경험 항목이 준비된 뒤
`published`로 전환한다.

## 9. 경험 카탈로그

### 9.1 범위

핵심 경험에는 다음이 포함된다.

- 코드에서 확인 가능한 기술 구현 경험
- 장애 대응, 모니터링과 운영처럼 직접 선택이 필요한 기술 경험

코드 리뷰, 협업과 기획 같은 비기술 경험은 MVP 회사 매칭 기준에서 제외한다.

### 9.2 구조

```json
{
  "id": "async-processing",
  "label": "비동기 작업 처리",
  "description": "요청과 오래 걸리는 작업을 분리해 처리해 봤다",
  "roleIds": ["backend", "data-ai"],
  "trackIds": ["application-backend", "data-engineering"],
  "verification": {
    "githubAnalysis": true,
    "strongEvidenceExamples": ["큐 생산·소비 코드", "재시도와 실패 처리"],
    "weakEvidenceExamples": ["Kafka·Celery 의존성만 존재"],
    "selfReportQuestion": "비동기 작업의 실행과 실패 처리를 직접 구현했나요?"
  },
  "status": "draft"
}
```

GitHub로 확인하기 어려운 기술 경험은 `githubAnalysis: false`로 두고 직접 선택
목록에만 표시한다.

### 9.3 게시 조건

경험 항목은 다음을 모두 통과해야 `published`가 된다.

1. 회사 프로젝트 하나 이상의 진입 또는 연결 경험으로 사용된다.
2. 다른 경험과 의미가 명확히 구분된다.
3. 특정 프레임워크 없이 행동 중심 문장으로 설명할 수 있다.
4. 강한 근거, 약한 근거와 판단 불가 사례를 정의할 수 있다.
5. 실제 저장소 표본에서 근거 없는 후보를 반복 생성하지 않는다.

현재 `data/experience.json`의 모든 항목은 다시 `draft`로 간주한다. 회사 조사
결과와 저장소 표본을 바탕으로 유지, 통합, 분리 또는 삭제한다. 새 카탈로그가
확정되면 버전을 올리고 현재 임시 입력은 마이그레이션하지 않는다.

### 9.4 프로젝트 맥락

현재의 `혼자 만들어 봄 / 팀 프로젝트 경험 / 운영 환경 경험` 단일 선택 그룹은
제거한다. 이 세 값은 하나의 진행 수준이 아니며 동시에 성립할 수 있다.

회사 프로젝트 연결에 필요한 배포, 모니터링과 장애 대응은 독립된 기술 경험
항목으로 표현한다. 혼자 또는 팀으로 했는지는 MVP에서 별도로 수집하지 않는다.

## 10. GitHub 근거 수집

### 10.1 항상 확인하는 자료

- README 일부
- 언어 비율과 전체 파일 트리
- 패키지, 빌드와 주요 설정 파일
- Docker와 CI/CD 설정
- 테스트 파일 존재 여부

### 10.2 직무별 파일 우선순위 예시

| 직무 | 경로·파일 신호 예시 |
|---|---|
| 서버·백엔드 | route, controller, service, repository, schema, migration |
| 웹 프론트엔드 | page, component, hook, store, API client, UI test |
| 데이터·AI | pipeline, ETL, notebook, model, evaluation, serving |
| 모바일 | screen, view model, networking, local storage, build 설정 |

파일 선택 규칙은 직무·세부 트랙 카탈로그와 함께 버전 관리한다.

### 10.3 초기 한도

- 저장소 최대 3개
- 저장소당 핵심 텍스트 파일 최대 8개
- 저장소당 입력 상한 약 4만 자
- 세 저장소 합계 상한 약 12만 자
- 출력 후보 저장소당 최대 8개
- 저장소별 분석을 병렬 실행

이 값들은 확정 예산이 아니라 초기 안전 상한이다. 목표 평균 입력은 저장소당
2만~2만 5천 자로 두고 실험 결과에 따라 조절한다.

### 10.4 제외 대상

- lock 파일, 바이너리와 minified 파일
- 빌드 결과물, vendor와 의존성 디렉터리
- `.env`, 인증서, 키와 자격증명 가능성이 있는 파일
- 크기 상한을 넘는 파일

지나치게 큰 파일은 임의로 일부만 잘라 강한 근거로 사용하지 않는다.

### 10.5 근거 참조

모든 근거는 분석 당시의 커밋 SHA, 파일 경로와 줄 범위를 가진다. 사용자에게
코드 원문을 저장해 보여주는 대신 해당 커밋의 GitHub 파일 링크를 만든다.

## 11. Claude 판정

### 11.1 출력 계약

```ts
type ExperienceCandidate = {
  experienceId: string;
  statement: string;
  evidenceLevel: "strong_signal" | "needs_confirmation";
  evidence: {
    repositoryUrl: string;
    commitSha: string;
    path: string;
    startLine: number;
    endLine: number;
    summary: string;
  }[];
  confirmationQuestion: string;
};
```

### 11.2 근거 등급

- 실제 구현 코드나 테스트에서 행동이 드러나면 `strong_signal` 후보가 될 수 있다.
- README 설명이나 의존성·설정만 존재하면 `needs_confirmation`이다.
- 개인 역할, 협업 방식과 코드에 없는 효과는 단정하지 않는다.
- 적합한 경험 ID가 없으면 억지로 매핑하지 않는다.
- 후보 수를 채우기 위해 추론하지 않는다.

서버는 README와 설정 파일만 인용한 `strong_signal`을 자동으로
`needs_confirmation`으로 낮춘다. 어느 등급도 사용자 확인 전에는 매칭 데이터가
아니다.

### 11.3 프롬프트 구조

1. 시스템 규칙과 신뢰 경계
2. 선택한 직무와 `published` 경험 카탈로그
3. 커밋 SHA와 줄 번호가 붙은 저장소 근거 묶음
4. JSON 출력 계약과 금지 사항

저장소 내용은 프롬프트 안에서 명확한 데이터 구분자로 감싼다. 저장소에 포함된
지시문은 실행할 명령이 아닌 분석 대상 텍스트로만 취급한다.

### 11.4 모델과 비용 실험

모델은 설계 시점에 확정하지 않는다. 같은 저장소 표본을 Claude Haiku 4.5와
Claude Sonnet 5에 실행해 정확도 기준을 만족하는 가장 저렴한 모델을 선택한다.

저장소당 입력 15,000~25,000토큰, 출력 800~1,500토큰을 가정한 표준 API 비용
추정치는 다음과 같다. 캐시와 Batch 할인은 제외했다.

| 모델 | 저장소 1개 | 저장소 3개 | 100명이 3개씩 |
|---|---:|---:|---:|
| Claude Haiku 4.5 | 약 $0.02~0.03 | 약 $0.06~0.10 | 약 $6~10 |
| Claude Sonnet 5 | 약 $0.04~0.07 | 약 $0.11~0.20 | 약 $11~20 |

가격은 변경될 수 있으므로 구현 시점의 공식 가격을 다시 확인한다.

- Haiku 4.5 공식 가격표: https://www-cdn.anthropic.com/files/4zrzovbb/website/3684c2faafb97418665782cea0001f439f74b1d2.pdf
- Sonnet 5 공식 안내: https://www.anthropic.com/news/claude-sonnet-5

모든 응답의 실제 `input_tokens`와 `output_tokens`로 비용을 계산한다.

### 11.5 버전

분석 결과에는 다음 버전을 함께 기록한다.

- `catalogVersion`
- `analysisVersion`
- `promptVersion`

프롬프트나 판정 기준이 바뀌면 버전을 올려 이전 세션 결과와 섞이지 않게 한다.

## 12. API

```http
POST /api/repository-analysis
```

```json
{
  "url": "https://github.com/user/repo",
  "roleId": "backend",
  "catalogVersion": 3,
  "consentVersion": 1
}
```

성공 응답:

```json
{
  "ok": true,
  "analysisVersion": 1,
  "repository": {
    "url": "https://github.com/user/repo",
    "commitSha": "abc123",
    "keywords": ["TypeScript", "NestJS", "PostgreSQL"]
  },
  "candidates": []
}
```

실패 이유:

- `invalid_url`
- `not_found_or_private`
- `github_rate_limited`
- `analysis_timeout`
- `analysis_budget_exceeded`
- `llm_unavailable`
- `invalid_llm_response`
- `no_usable_evidence`

저장소별 요청을 최대 3개까지 브라우저에서 병렬 실행한다. 서버도 저장소 수,
파일 수와 입력 크기 제한을 다시 검증한다.

## 13. 브라우저 저장

### 13.1 sessionStorage

분석 결과, 미확정 후보와 거절 상태를 현재 흐름 동안만 보관한다.

```ts
type RepositoryAnalysis = {
  url: string;
  commitSha: string;
  roleId: string;
  catalogVersion: number;
  analysisVersion: number;
  promptVersion: number;
  keywords: string[];
  candidates: ExperienceCandidate[];
};

type CandidateDecision = {
  experienceId: string;
  status: "pending" | "confirmed" | "rejected";
  evidenceRefs: string[];
};
```

같은 세션에서 뒤로 갔다 돌아오면 분석을 재사용한다. 사용자가 `다시 분석`을
선택했을 때만 최신 커밋을 조회한다.

### 13.2 localStorage

회사 매칭에 사용할 최종 확인값만 직무별로 저장한다.

```ts
type ExperienceProfile = {
  roleId: string;
  catalogVersion: number;
  confirmedExperiences: {
    experienceId: string;
    origins: ("github" | "manual")[];
    evidenceRefs?: string[];
  }[];
};
```

거절·미검토 후보와 소스 코드 내용은 최종 프로필에 저장하지 않는다. 카탈로그
버전이 바뀌면 해당 직무 프로필을 다시 확인하도록 안내한다.

## 14. 3단계 사용자 경험

### 14.1 GitHub 분석 결과가 있는 경우

첫 섹션에 `GitHub에서 찾은 경험 후보`를 표시한다. 카드에는 다음이 들어간다.

- 저장소에 맞춘 경험 문장
- `구현 근거 있음` 또는 `확인 필요` 배지
- 저장소와 파일 근거 링크
- 사용자의 담당 여부 확인 질문
- `내가 한 경험이에요`와 `아니에요` 동작

후보는 기본 선택하지 않는다. 미검토 후보와 거절 후보는 매칭에서 제외한다.

두 번째 섹션 `GitHub에서 찾지 못한 경험 추가`에서 고정 경험 목록을 직접 선택할
수 있다.

### 14.2 GitHub가 없는 경우

AI 후보 섹션 없이 고정 경험 목록에서 바로 선택한다. 최종 저장 형식은 GitHub
사용자와 같다.

### 14.3 제출 조건

최소 한 개의 경험을 확인하거나 직접 선택하면 진행할 수 있다. 모든 AI 후보를
검토하도록 강제하지 않으며 미검토 후보는 제외한다.

## 15. 회사 프로젝트 연결

회사 프로젝트 제안은 사용자 경험과 연결되는 안정적인 ID를 가진다.

```json
{
  "id": "payment-idempotency",
  "title": "중복 결제를 방지하는 요청 처리 만들기",
  "roleId": "backend",
  "trackIds": ["application-backend"],
  "entryExperienceIds": [
    "rest-api-design",
    "db-design",
    "concurrency-control"
  ],
  "bridgeExperienceIds": [
    "transaction-handling",
    "request-validation"
  ],
  "evidenceIds": ["job-12", "blog-7"]
}
```

- `entryExperienceIds`: 프로젝트를 바로 더 깊게 발전시킬 수 있는 경험
- `bridgeExperienceIds`: 한 가지 경험을 보완하면 이어질 수 있는 기초 경험

판정은 다음처럼 결정적으로 수행한다.

| 단계 | 판정 |
|---|---|
| `fit` | 하나 이상의 프로젝트가 확인 경험과 `entryExperienceIds`로 연결됨 |
| `step` | 직접 연결은 없고 `bridgeExperienceIds`로 연결됨 |
| `far` | 두 연결 모두 없음 |

한 회사에 여러 프로젝트가 있으면 가장 가까운 프로젝트를 대표 이유로 보여준다.
회사를 점수나 퍼센트로 줄 세우지 않는다. 같은 단계 안에서는 회사명이나 근거
최신성과 같은 비개인적 기준만 사용한다.

모든 프로젝트 연결은 회사 채용 공고 또는 기술 블로그 근거를 가져야 한다. 연결
ID가 없거나 근거가 검증되지 않은 프로젝트는 매칭에 사용하지 않는다.

## 16. 오류 처리

각 저장소는 독립된 상태를 가진다.

```text
대기 → 저장소 확인 → 파일 선별 → 경험 분석 → 완료
                                  ↘ 실패
```

세 저장소 중 하나가 실패해도 성공 결과는 유지한다. 실패한 저장소에만 재분석
동작을 제공하고 직접 경험 입력으로 항상 진행할 수 있게 한다. 자동 재시도는
비용을 예측하기 어렵게 하므로 MVP에서 하지 않는다.

사용자 메시지는 구현 상세 대신 복구 방법을 설명한다.

- 저장소 없음·비공개: 공개 저장소를 찾지 못했음을 안내
- GitHub 한도: 현재 조회가 지연되고 있음을 안내
- 시간 초과·LLM 장애: 직접 경험을 선택할 수 있음을 안내
- 분석 자료 없음: 경험을 판단할 코드 근거가 부족함을 안내

## 17. 보안과 개인정보

- 공개 GitHub 저장소만 분석한다.
- GitHub API 이외의 사용자 제공 URL로 서버 요청을 보내지 않는다.
- README의 링크나 명령을 실행하거나 방문하지 않는다.
- 저장소 내용은 신뢰할 수 없는 데이터로 취급한다.
- Claude에는 파일 읽기나 외부 호출 도구를 제공하지 않는다.
- 자격증명 가능성이 있는 파일을 제외하고 비밀키 형태 문자열을 추가로 마스킹한다.
- LLM이 반환한 URL은 사용하지 않고 검증된 저장소 경로로 링크를 생성한다.
- 서버는 코드 원문과 분석 결과를 저장하지 않는다.
- 저장소 코드 일부가 Claude API로 전송된다는 사실을 분석 전에 명시한다.
- 로그에는 처리 시간, 입력량, 후보 수와 오류 코드만 기록한다.
- 코드 내용, Claude 응답 본문과 비밀값은 로그에 기록하지 않는다.

## 18. 비기능 요구사항

### 성능

- 저장소 최대 3개의 전체 분석 목표: 20~30초
- 단계별 진행 상태 표시
- 저장소별 병렬 처리

### 규모

- 데모·심사 규모와 하루 수십 회 분석을 우선 지원
- 대규모 트래픽 최적화는 비목표

### 신뢰성

- 부분 성공 허용
- 외부 API 실패 시 직접 입력으로 대체
- 한 요청의 실패가 다른 저장소 결과를 지우지 않음

### 유지보수

- 직무, 세부 트랙과 경험 카탈로그를 버전 관리
- 새 경험은 팀 검토 후에만 `published`
- LLM이 새 경험 ID를 자동 생성하거나 게시하지 않음

## 19. 검증 계획

실제 사용자가 내용을 아는 공개 저장소 8~12개를 사용한다. 네 상위 직무,
개인·팀 프로젝트와 문서가 충분하거나 부족한 저장소를 가능한 범위에서 섞는다.

후보마다 다음을 별도로 평가한다.

1. 저장소 근거가 경험을 실제로 뒷받침하는지
2. 저장소 참여자가 해당 부분을 직접 담당했는지

초기 MVP 통과 기준:

- 존재하지 않는 경험 ID·파일 경로·줄 번호: 0건
- `구현 근거 있음` 후보의 근거 정확도: 90% 이상
- 근거 없는 성능 수치나 개인 역할 단정: 0건
- 참여자가 확인한 전체 후보 비율: 70% 이상
- 최대 3개 분석의 90%가 30초 안에 완료
- 일부 저장소 실패 후 직접 입력 완료 가능: 100%

후보 누락률은 기록하되 첫 버전에서는 잘못된 후보를 줄이는 것을 우선한다.

테스트 계층:

- 순수 함수: URL 파싱, 파일 제외·선별, 중복 병합과 회사 단계 판정
- 계약: 잘못된 ID·경로·줄 범위와 비정상 LLM 응답 거부
- API 통합: 고정 GitHub·Claude fixture로 성공과 오류 재현
- 화면: 전체 성공, 일부 실패, 전체 실패와 GitHub 미사용 흐름
- 수동: 실제 공개 저장소와 커밋 고정 근거 링크 확인

## 20. 구현 순서

### 1단계 — 공통 데이터 계약

- 상위 직무와 세부 트랙 스키마
- 경험 카탈로그 스키마
- 회사 프로젝트 연결 ID
- 버전과 `draft/published` 상태

### 2단계 — GitHub 근거 수집기

- 현재 기술 키워드 추출 유지
- 파일 제외, 우선순위와 크기 제한
- 커밋 SHA와 줄 번호가 포함된 근거 묶음
- Claude 없이 fixture 기반 검증

### 3단계 — Claude 비교 실험

- 임시 경험 카탈로그로 구조화 출력 구현
- Haiku와 Sonnet에 동일 근거 입력
- 정확도, 시간, 토큰과 예상 비용 비교
- 모델과 입력 한도 결정

### 4단계 — 사용자 확인 화면

- GitHub 후보 확인과 근거 링크
- 누락 경험 직접 추가
- GitHub 없음과 분석 실패 분기
- 기존 단일 진행 수준 UI 제거

### 5단계 — 회사 연결

회사 조사 결과가 준비되면 경험 ID를 연결하고 `fit/step/far` 판정을 활성화한다.
그전에는 근거 없는 임시 회사 분류를 만들지 않는다.

1~4단계는 회사 조사와 병렬로 진행할 수 있다.
